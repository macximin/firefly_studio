# 집필 중 등장하는 인물·회사 기록 연결

2026-09-06 · InkOS 로컬 구현

새 인물과 회사가 본문에 등장하면 기존 정산 단계에서 이름과 원문 근거를 추출하고, 다음 회차 기획·집필에 전달한다. 사람이 검토 중인 p01 기획서는 유지한다.

## 바뀐 동작

1. 기존 Observer와 Settler가 이름으로 등장하거나 언급된 인물, 회사·그룹·기관·조직을 확인한다. 새 인물뿐 아니라 기존 인물의 소속·직책·관계·상태 변화도 본문 근거로 기록한다. 모델 호출 단계는 추가하지 않는다.
2. 기록은 `story/state/current_state.json`의 선택 필드 `entityObservations`에 저장한다. 항목은 `kind`, `name`, `evidence`, `sourceChapter`, `chapterTextHash`다. 회차와 본문 해시는 호스트가 붙인다. 초기 `story/roles/` 카드와 세계관을 덮어쓰지 않는다.
3. 근거는 이름을 포함하는 본문의 연속된 정확한 인용이어야 한다. 본문에 없는 나이·소속·지분·과거를 별도 사실로 보충할 수 없다. 같은 이름의 인물과 회사를 구분하며, 이름이나 별칭만으로 동일 인물이라고 합치지 않는다. 대사·의혹·주장도 문맥을 보존한 관찰로 전달한다.
4. 저장할 때 최종 본문을 기준으로 다시 검증한다. 수정한 같은 회차의 이전 기록은 전량 교체하고 앞 회차 기록은 유지한다. 캐시된 관측 정보는 신뢰하지 않되, 정산 후 호스트가 확정한 복선 승격 결과는 유지한다.
5. 기록이 기존 회차 상태 안에 있으므로 본문·상태의 원자적 저장, 실패 시 복구, 회차 수정·삭제·스냅샷 복원에 함께 묶인다. 상태 검증 실패로 본문만 보존하는 `state-degraded`에서는 기록도 전진하지 않는다. 별도 등록 파일을 추가하지 않아 구버전 스냅샷 복원 뒤 미래 기록이 남는 문제를 피한다.
6. Planner, Composer, Writer의 실제 모델 입력에 연결한다. 현재 회차 직전까지의 기록만 읽고, 목표에 이름이 직접 걸리는 기록과 최근 기록을 우선한다. 역할카드가 이미 있어도 추가 기록을 읽는다. Writer에 오래된 입력 묶음을 전달해도 해당 기록은 현재 저장 상태에서 다시 읽는다.

## 입력 분량과 확인 위치

- 회차별 추출은 최대 128항목, 이름은 120자, 한 인용은 1,200자다. 전체 누적 기록을 매번 모델에 넣지 않는다.
- 한 번에 전달하는 기록은 안내를 포함해 최대 6,000자다. 인용을 중간에서 자르지 않는다. Composer가 선택한 기록은 압축 과정에서 인용이 바뀌지 않게 보호하고 기존 전체 입력 예산 검사를 받는다.
- Writer가 기존 선택을 새로 읽을 때는 기존 기록 슬롯의 문자·추정 토큰 상한을 모두 지킨다. 슬롯이 없고 모델의 컨텍스트 크기를 알 수 있으면 기존 선택과 출력 예약량을 제외한 범위에서 추가한다. 모델 크기가 없는 직접 호출은 6,000자 상한을 쓴다.
- 누적 기록: 각 Book의 `story/state/current_state.json`.
- Composer 선택 근거: 기존 회차 `context.json`과 trace의 `story/state/current_state.json#entity-observations` 항목.
- 실제 Writer 전달 기록: `story/runtime/chapter-NNNN.entity-context.json`. Composer 이후 새로 읽은 내용과 직전 회차 한계, 추정 토큰을 남긴다. 이 파일은 집필 입력 확인용이며 정본 저장소가 아니다.

## 호환과 범위

기존 구조화 상태와 과거 delta는 추가 필드 없이도 읽힌다. 새 Settler 실행은 구조화된 delta와 `entityObservations` 배열을 반드시 내야 한다. 해당 기록이 없으면 `[]`를 명시한다. 잘못된 JSON, 누락된 배열, 구형 텍스트 응답을 정상 완료로 취급하여 등록을 건너뛰지 않는다. 과거 텍스트를 읽는 별도 legacy parser는 유지한다.

이 기능은 관찰 기록과 전달의 연결이다. 이름이 있는 모든 대상을 모델이 빠짐없이 찾아냈다는 의미 검증까지 기계적으로 증명하지는 않는다. 저장되는 인용의 실재 여부는 검사하지만, 인물/조직의 의미 분류와 충분한 근거 선택은 모델 품질에 달려 있다. 별칭 통합, 동명이인 식별, 기록을 인물의 현재 속성으로 합치는 작업은 이번 범위에 넣지 않았다. 과거 원고의 자동 소급 분석도 실행하지 않았다.

현재 기획 HIL의 계약·문서·사람 선택, 모델 설정, 실제 Book 생성, 원고 생성과 Storyyard 배포는 변경하지 않았다. source-first 기획의 Book 승격 지원 여부도 이 작업으로 바뀌지 않는다.

## 검증

검증은 임시 Book과 모의 모델 응답을 이용했다. 실제 생성 모델의 추출 성능을 측정한 카나리는 아니다.

새 단위 17개·통합 18개를 포함하여 중복을 제외한 관련 검사 350개가 통과했다. 넓은 회귀 검사 344개를 먼저 통과했고, 최종 수정 뒤 영향받는 163개를 다시 확인했다. Core/CLI 빌드와 변경 공백 검사도 통과했다.

- 본문 근거 검증, 동일 이름의 인물/회사 분리, 수정 시 삭제, 재실행, 앞 회차 보존, 오래된 스냅샷 복원, 늦은 저장 실패 복구.
- 초기 역할카드가 있는 상태에서 저장한 새 기록이 다음 Writer의 legacy/v2 경로와 Planner의 실제 모델 요청에 도달하는지 확인. 인접 원고에서 우연히 같은 문장이 유입되는 경로는 차단하여 기록 연결 자체를 검증했다.
- 미래 회차·삭제된 관측의 캐시 유출 방지, 입력 분량 제한, Compressor의 인용 보호, 정산 누락·허위 근거 거부, 상태 검증 실패 시 원고만 보존하는 경계.
- 기존 Writer·Planner·Composer·상태 저장·복구·전체 회차 실행 회귀 검사와 Core/CLI 빌드.

정확한 검사 수, 실행 결과와 코드 해시는 [검증 기록](evidence/entity-observations-20260906/verification.json)에 남긴다. 작업 시작과 비교하여 현재 카나리·설정 136개 파일이 동일하고 실제 Book 디렉터리가 생성되지 않았음을 확인했다.
