# 변주 후보도 같은 작품 기획서로 표시

사용자 지시: 변주안은 별도 변경 보고서가 아니라 기존과 같은 기획서로 읽혀야 한다. 합의한 `webnovel-project-plan/v1`의 1~9절을 사용하며, 2절에 WHO·WHAT·HOW·WHERE·WHEN·WHY를 표시한다. WHAT은 작품 전체의 진행과 목적, HOW는 우위를 얻고 자신의 이익으로 바꾸는 작동 원리를 설명한다. 첫 사건의 작업 목록만으로 이 두 항목을 대신하지 않는다.

## 현재 두 후보

현재 검토 묶음 `frp-30945a8618f92b17b5069c1c`의 v01과 v02를 동일한 9절 양식으로 정리했다. 기준 기획의 인물 배경과 장기 목적, 현재 후보의 사건·연대·금액·인물, 이번 사용자 설명을 사용했다. 별도 모델 실행을 했다고 기록하지 않는다.

- InkOS 작성물: `.inkos/source-first-canaries/chaebol-planning-format-20260906-v1/authored/`
- InkOS 내보내기: 같은 실행 폴더의 `export/project-plans.json`, `receipt.json`
- Storyyard 투영: `data/firefly/planning-documents/index.json`

이미 기록된 후보·독립 심사·패킷은 그대로 보존하고, 작성한 기획서는 정확한 패킷과 후보 SHA에 연결한다. Storyyard는 InkOS에서 내보낸 본문을 검증해 그대로 표시한다. 원본 판정은 변주 선택이며 원고 적용이나 정본 채택으로 승격하지 않는다. 독립 심사는 기존 후보에 대한 심사 기록으로 유지한다.

v01은 미래 경제 사건 기억으로 투자 방향과 회수 시점을 선점하고, 수익으로 기업 지분을 산다. v02의 현재 사업 기회는 실제 매각 자료·고객 조사에서 나오며, 미래 기억은 위험 판단에 사용된다. 서로 다른 후보의 원리를 같다고 꾸미지 않는다. 미래 상세 사건은 미정으로 남긴다.

## 이후 InkOS 실행

새 변주 지침 v2는 기준 기획서 전체를 해시로 연결해 입력하고, 후보 안에 기존 형식의 `projectPlan`을 요구한다. 아홉 절의 순서와 내용, 육하원칙을 검증한다. 새 후보의 사람 검토용 Markdown은 기획서 본문만 내보낸다. 사건 비교 구조는 내부 근거로 보존한다.

기존 무표지·v1 요청의 프롬프트와 출력은 유지해 과거 실행 영수증이 재현되도록 한다. `scripts/export-variation-project-plans.mjs`는 기존 후보를 이번 양식으로 표시하기 위한 내보내기이며 새 작품 생성이나 모델 실행으로 취급하지 않는다.

## 표시와 보존

현재 두 후보의 링크에서 기획서를 바로 읽는다. 이전 기준안, 수정 내역, 비교표를 본문 위에 끼워 넣지 않는다. 이전 17개 검토 묶음의 보관 상태, 기존 사람 코멘트와 판정은 유지한다.
