# 웹·Hermes 다중 모델 기획 생산과 작성자 표시 계획

> 당시 계획 기록. 현재 여섯 경로·Grok CLI 가용 여부·별도 Storyyard 기획 반입·미완성 InkOS 인계는 [피치 정책·연결 상태](pitch-policy-status.md)를 기준으로 한다. 아래의 “정기 실행은 아직 만들지 않았다” 및 재시험·반입 제약은 당시 상태다.

2026-09-06 · 초기 계획과 후속 결정. 이후 사용자가 최신 로컬 양식으로 카나리를 승인하여 12경로 비교와 Storyyard 반입을 완료했다. 실제 결과와 한계는 [카나리 보고서](2026-09-06-twelve-route-planning-canary.md)를 기준으로 한다. 아래의 핑 단계 제약과 준비 표는 당시 기록이다.

최신 운용 결정: OpenCode 무료 6모델을 후속 생성에서 제외하고 기존 결과·영수증은 보존한다. 원래 6경로는 유지하되 Grok CLI는 긴 작업 실행 문제를 고친 뒤 재시험해야 한다. [제외 정책과 관제 대안](2026-09-06-planning-route-retirement.md)을 참조한다. 정기 실행은 아직 만들지 않았다.

연결 후속 확인: Hermes → Grok CLI 핑 통과. Google은 기존 Gemini CLI가 아닌 설치된 Antigravity CLI → Gemini 경로로 핑 통과했다. 개인 구독 CLI의 공식 전환에 따른 권장 대안이며 원래 요청 경로를 조용히 바꿔 기록하지 않는다. 상세는 `2026-09-06-hermes-grok-google-cli-followup.md`를 참조한다.

추론 설정 후속: 웹은 현재 가용 최고인 ChatGPT `6 Pro`, Grok `4.6 전문가`, Gemini `3.1 Pro Extended`를 기준으로 한다. 매 실행 전 UI에서 재확인하며 Gemini Extended는 새로고침 후 풀리므로 재선택한다. CLI는 Grok `grok-4.6 / high`, Antigravity Gemini `gemini-3.1-pro-high / high` 지정 핑을 통과했다. 세부 범위와 전역 기본값 미변경은 `2026-09-06-high-reasoning-route-settings.md`에 기록했다.

장기 목표는 기존 성공작의 원문과 역설계 자산을 활용해 사용자 취향에 맞는 완전한 기획서를 하루 약 10개 만들고, 현재 Storyyard에서 출처를 확인하며 비교·판정하는 것이다. 사용자가 이번 첫 시험을 현대판타지 6개로 확정했다. 이후 판타지와 무협도 각각 6개씩 순서대로 진행한다. 첫 시험에 하루 10개 할당을 적용하지 않는다. 이번 범위는 기획서까지다. A/B레일 설계와 InkOS 집필은 채택 이후 별도 작업으로 남긴다.

## 1. 결정 방향

- V3를 기획 작업 공간으로 한정해 수선한다. 옛 V3 전체 자동화를 복원하지 않는다.
- 브라우저 작업은 사용자가 지정한 ego lite / ego-browser를 기본으로 한다. 로그인·UI 차이가 없어지는 것으로 가정하지 않고 각 작업 공간에서 확인한다.
- Hermes 실행과 웹 서비스 작성을 모두 수용한다. 웹 결과를 API나 Hermes 생성으로 바꿔 기록하지 않는다.
- 웹 Gemini, 웹 Grok, ChatGPT 웹 대화를 작성 경로에 포함한다. 사용자 추가 설명에 따라 OpenAI 웹 경로의 기본값은 ChatGPT로 정한다. Codex cloud는 저장소·실행 환경 기반의 별도 경로이며 이번 초기 웹 비교에 필수로 넣지 않는다.
- 모든 신규·변주 기획서는 합의한 `webnovel-project-plan/v1` 9절과 육하원칙을 사용한다. 작성자 표시는 본문을 바꾸지 않는 머리말·카드 정보로 둔다.
- Reference Lab의 기존 15편 기획서 및 구조 분석부터 재사용한다. 분석 파일 존재를 전체 품질 승인으로 취급하지 않고, 필요한 부분만 원문과 대조한다.
- 기존 InkOS Hermes 모델·작성·심사 설정은 유지한다. V3 기획 전용 프로필과 연결을 추가한다.
- Storyyard를 기획 검토와 HIL의 중심으로 쓴다. 같은 상태를 Notion·ClickUp에 중복 입력하지 않는다.

## 2. 확인한 현행 제약

- 현재 V3 pitch 템플릿은 자유 순서와 옛 모델 지침, 인물 수 등 고정 조건을 포함한다. 현재 9절 요구에 맞는 기획 경로가 필요하다.
- 현재 InkOS `pitch-variation.ts` v5 패킷은 `source.system=inkos`로 고정되어 있다.
- 확인한 Storyyard 작업 사본의 `app/firefly-planning-documents.ts`는 `inkos-variation-project-plans/v1`과 `sourceSystem=inkos`만 받는다.
- 기존 V3 exporter는 승인 원고와 특정 과거 작품 경로를 전제로 하므로 미승인 웹 기획서 수입에 그대로 사용하지 않는다.
- Hermes의 제공자별 실제 인증·가용 모델·한도, 각 웹 서비스의 파일 입력·결과 반출 방식은 구현 시 짧은 실제 시험으로 확인한다. 서비스 보유를 자동화 연결 성공으로 간주하지 않는다.

근거: `2026-09-06-v3-storyyard-hermes-planning-audit.md`, `2026-09-06-financial-variation-material-hil.md`, 현행 템플릿과 패킷 코드. 이 문서는 운영 사이트의 새 배포 확인을 주장하지 않는다.

## 3. 작성자 태그와 이력

일반 보기의 카드와 기획서 상단에 다음 정보를 표시한다.

| 표시 | 예시 또는 규칙 |
| --- | --- |
| 작성 서비스·경로 | Gemini · 웹 / Grok · 웹 / ChatGPT · 웹 / Codex CLI / 제공자 API |
| 모델·모드 | 실제 화면 또는 실행 응답에서 확인한 이름. 모르면 모델 미확인 |
| 기획 담당 프로필 | Hermes 프로필 표시명 또는 웹에 전달한 역할 지침 이름 |
| 버전·작성 시각 | 해당 후보 revision과 생성 시각. 반입 시각과 구분 |
| 수정·검토 | 초안 작성자와 다른 주체가 내용 수정·검토했으면 구분해 표시 |

Hermes는 실행 관리자이고 작성 모델과 별개다. 예를 들어 `작성: Gemini · 웹`, `수정: Codex · CLI`, `관리: Hermes`를 각각 남긴다. 웹 계정의 개인 이메일·인증 정보는 표시하거나 저장하지 않는다.

보조 기록에는 제공자, 제품 화면, 전달 방식(web/cli/api), 실행 관리자, 모델·추론 모드, 확인 근거, 작업/대화 링크(있을 때), 입력 묶음 버전, 원본 응답 해시, 수정 부모 버전, 담당 역할을 보존한다. 사용자가 입력한 모델명은 사용자 신고, 화면에서 확인한 모델명은 화면 확인으로 구분한다. 웹 UI에 표시된 이름을 내부 실제 모델 식별자로 과장하지 않는다.

작품과 후보의 ID는 모델 변경과 분리한다. 기존 후보를 다른 모델이 수정하면 새 revision으로 남기고, 새로운 대안이면 별도 후보로 만든다. 대화 URL 접근 가능 여부와 무관하게 반입 당시 원문을 보존한다.

블라인드 비교는 선택 기능이다. 기본은 사용자 요청대로 작성자 태그를 보인다. 블라인드 모드에서는 태그를 화면에서만 숨기며 출처 기록을 지우지 않는다.

## 4. 공통 입력과 두 가지 작성 경로

공통 입력은 원작·역설계 자료, 이번 조합의 목적과 변주 범위, 취향 지침, 실제 채택·보류 예시, 9절 양식, 출력 방법으로 구성한다. 긴 대화 전체를 매번 넣지 않고 이번 작업과 관련된 맥락을 준비한다. 근거 원문은 다시 확인할 수 있어야 한다.

### Hermes 실행

검증된 제공자 연결로 새 세션을 실행하고 원본 응답과 실행 영수증을 보존한다. 작성과 독립 검토는 입력·세션을 구분한다. 응답 실패나 형식 오류가 나면 실패를 기록하며, 다른 모델로 대신 쓴 결과를 원래 모델의 성공으로 기록하지 않는다.

### 웹 작성

1. 같은 공통 입력을 웹에서 읽을 수 있는 Markdown과 필요한 첨부 묶음으로 준비한다.
2. 해당 웹 서비스에 전달하고 기획서를 작성한다. 실제 자동 조작 지원 여부를 먼저 확인하며 브라우저 접속 성공을 생성 성공으로 간주하지 않는다.
3. 완성 응답을 파일 내보내기 또는 복사·붙여넣기로 반입한다. 브라우저 자동화가 불안정해도 수동 반입으로 동일한 공정에 합류할 수 있게 한다.
4. 원본을 보존하고 출처 정보를 붙인 뒤 9절·육하원칙과 완결 여부를 검사한다.
5. 내용 보완이 필요하면 별도 수정 작업으로 요청한다. 반입 도구가 누락 내용을 몰래 창작하거나 출처를 바꾸지 않는다.

웹 화면·첨부 한도·숨은 대화 맥락에 따라 입력이 달라지면 차이를 기록한다. 같은 모델의 웹과 API/CLI 결과도 별도 경로로 비교한다. 자동 반입 중 원문이나 응답 안의 지시문을 운영 명령으로 실행하지 않는다.

## 5. 취향 반영

고정 취향, 장르별 선호, 해당 후보의 수정 요청을 구분한다. 자기중심성은 주인공 자신의 이득·목적이 선택을 이끄는 것으로 적용한다. 원작에 있는 가족애 등 사실은 지우지 않는다.

이번 펌프·판매망 보류는 모든 비주류 업종 금지가 아니다. 얻는 대상 자체가 탐나고 사건이 읽고 싶어야 한다는 기준으로, 사용자 코멘트와 해당 기획서의 실제 대목을 함께 남긴다. 통과한 구체 예시도 함께 사용한다.

Storyyard HIL은 정확한 후보 revision에 묶는다. 다음 생성 전에 관련 판정을 입력에 포함했는지 확인하고 적용 버전을 기록한다. 모델의 영구 학습이나 자동 취향 학습 완료라고 부르지 않는다. 모호한 코멘트를 전 작품 금지 규칙으로 자동 승격하지 않는다.

## 6. 확정한 첫 시험: 현대판타지 6개

각 경로에서 같은 공통 입력으로 기획서 한 편을 독립 작성한다. 사용자 표현의 한 장은 기획서 한 편으로 해석하며, 합의한 9절을 A4 한 페이지 요약으로 축소하지 않는다.

| 번호 | 작성 경로 | 준비·확인 사항 |
| --- | --- | --- |
| 1 | 웹 Gemini: https://gemini.google.com/app?hl=ko | 실제 모델·모드·첨부·반출 확인 |
| 2 | Hermes → Gemini CLI | 현재 셸 PATH에서 `gemini` 미발견. 설치 위치·연결·컨텍스트 전달 확인 필요 |
| 3 | 웹 Grok: https://grok.com/ | 2026-09-06 사용자 Chrome 탭에서 로그인 화면, 선택된 `전문가 · Grok 4.6`, 첨부 버튼 확인. 실제 파일 전달·생성은 아직 안 함 |
| 4 | Hermes → Grok CLI | `/Users/a2501/.grok/bin/grok` 설치 확인. Hermes 호출 연결과 공통 입력 전달은 별도 검증 |
| 5 | 웹 ChatGPT: https://chatgpt.com/ | 실제 모델·모드·첨부·반출 확인 |
| 6 | Hermes → GPT Astra | 기존 Astra 프로필과 입력 전달 로직 재사용 가능성을 확인하되, V3 기획용 별도 실행으로 구성 |

웹 Grok 메뉴에는 자동·빠른·전문가·Build·헤비가 표시됐다. 전문가가 선택된 상태만 읽었으며 모드를 변경하지 않았다. 웹 UI에 표시된 Grok 4.6을 모델 내부 식별자 검증으로 과장하지 않는다. 다른 웹 서비스의 가용성은 이 화면으로 추정하지 않는다.

Hermes의 Gemini/xAI 제공자 코드 존재는 Gemini/Grok CLI 실행 연결과 다르다. 요청한 CLI 경로를 API 호출로 몰래 대체하지 않는다. 기존 InkOS의 현대판타지·판타지·무협 프로필은 현재 Astra high이며 변경하지 않는다. 일반 `firefly-studio` 프로필은 Terra medium이므로 해당 이름만 보고 Astra 실행으로 판단하지 않는다.

### 같은 재료, 독립된 기획

현대판타지는 회차마다 주요 작품 3편을 선정하되 같은 세 작품을 영구 고정하지 않는다. 재벌·투자형에만 쏠리지 않게 기존 코퍼스에서 다른 하위 유형의 검증된 작품 묶음도 로테이션한다. 한 비교 회차 안에서는 여섯 경로에 같은 세 작품을 제공하고, 다음 회차에서 묶음을 바꾼다. 주축 《독식하는 재벌 3세》와 보조 《금수저 투자백서》·《연봉 1조 신입사원》은 가능한 한 묶음의 예시다. 이미 있는 분석과 원문을 쓰며 최종 조합 역할은 관련 사건을 다시 대조해 정한다. 독식의 재벌·회귀·사람 판독·자기 자본 축을 출발 후보로 두고, 보조 작품의 실제 투자·인재·사업 사건 중 맞는 것을 고른다. 다른 작품의 주인공 능력이 다르면 능력·정보·자원 조건을 같이 확인한다.

모든 경로에 원문, 기존 분석의 해당 부분, 원작별 구체 사건과 보상, 자기중심성·목적성, 조합 허용 범위, 9절 양식을 동일하게 제공한다. 웹에도 CLI와 같은 취향·맥락 문서를 전달한다. 웹에서 읽을 수 없는 로컬 경로만 적어 주지 않는다. 길이 제한 때문에 입력을 줄여야 하면 조용히 한 경로만 축약하지 말고 공통 자료를 재편성하거나 조건 차이를 기록한다.

원문 사실 복원과 새 기획 선택을 구분한다. 읽지 않은 후반 사건을 새로 지어 원작 분석에 섞지 않는다. 모델은 같은 자료 안에서 조합을 선택할 수 있지만, 앞서 다른 모델이 만든 후보는 읽지 않는다. 숨은 웹 기억·프로젝트 지침·도구 차이가 있으므로 결과는 순수 모델 성능보다 각 실제 작성 경로의 적합성 비교로 해석한다. 한 번의 6개 결과로 우열을 영구 확정하지 않는다.

### 변주의 정도

- 먼저 실제 성공작의 주인공 목적·우위·구체 사건·획득 대상·전개 연결을 복원한다.
- 주축 이야기의 매력을 유지하면서 다른 작품에서 맞는 사건·인물 관계·보상 방식을 조합한다. 모든 모델에 새로운 직업·업종·능력 발명을 요구하지 않는다.
- 연회·시계 폭로처럼 원작을 강하게 연상시키는 고유 장면은 능력 증명과 주인공 이득이 살아 있는 다른 사건으로 바꾼다. 비슷한 물건으로 명칭만 치환하지 않는다.
- 현실 시대·금융 사건·일반 장르 요소까지 무조건 새로 만들지 않는다. 인물 고유명·대사·독특한 장면 구성의 복제와 일반 소재 공유를 구분한다.
- 조합 때문에 시대·자본·능력·인물 동기가 충돌하면 연결에 필요한 만큼 수정한다. 새 권한·서류·승인 절차를 덧붙여서만 인과를 해결하지 않는다.
- 원작별 무엇을 취했는지와 변경 이유는 작업 근거로 남기되, Storyyard 본문은 완전한 기획서로 보여 준다. 별도의 수정 보고서로 대체하지 않는다.

### 실제 처리 순서

1. 기존 원문·분석을 대조해 현대판타지 공통 입력을 완성한다. 선택한 자료와 보류 사유를 묶어 여섯 경로에 같은 버전을 전달한다.
2. 웹은 첨부·복사 입력과 결과 수집, CLI는 Hermes 실행과 자료 읽기까지 짧은 경로 검증을 한다. 계획 단계에서 실제 기획 생성은 하지 않는다.
3. V3 기획 출력과 외부 작성자 메타데이터를 현재 Storyyard에 연결한다. 모든 결과는 기존 9절·육하원칙과 작성자 태그로 표시한다.
4. 여섯 독립 세션에서 한 편씩 생성한다. 원본 응답을 보존하고, 내용 수정 전의 첫 결과를 비교 기준으로 둔다. 다른 모델이 몰래 윤문해 여섯 작성자의 차이를 없애지 않는다.
5. 누락·출처·인과·심한 유사성을 검토하되 비평과 작성 본문을 분리한다. 형식 미완성도 상태로 남기고, 필요하면 원래 작성 경로에 한 번 보완을 요청해 새 revision으로 보존한다.
6. Storyyard의 같은 비교 묶음에 여섯 후보를 올린다. 후보별 작성자·모드·완료/미완료와 전문을 확인할 수 있게 하고, 본문 이외의 검사 기록은 접어 둔다. 추천은 사용자 선택을 대신하지 않는다.
7. 사용자는 Storyyard에서 채택·보류·탈락 및 이유를 남긴다. 그 판정을 다음 후보·수정 입력에 반영한다. 판타지, 무협은 각각 별도 원작 묶음으로 같은 여섯 경로를 반복한다.

첫 비교의 완료는 여섯 기획서가 모두 읽히고 실제 출처가 일치하며 판정이 정확한 후보 버전에 연결된 상태다. 연결 실패가 있으면 해당 경로를 미완료로 보고하며 다른 모델의 결과로 여섯 칸을 채우지 않는다. 사용자 품질 판정 전에는 이 공정이 성공했다고 확정하지 않는다.

### 이후 하루 10개 운영안

- 목표는 제목·로그라인 10개가 아니라 9절을 갖춘 기획 후보 약 10개다. 형식만 통과했다고 재미가 검증된 것으로 간주하지 않는다.
- 첫 비교에서는 실제 연결 가능한 웹·Hermes 경로에 동일한 재료를 주고 결과를 확인한다. 각 모델의 역할은 사용자 선택 결과를 본 뒤 배분한다.
- 본 운영의 예시는 원작 조합 5개에 대안 2개씩이다. 고정 할당은 아니며 모델별 사용 가능량과 기획 다양성에 따라 조정한다. 모든 모델에 10개씩 요청하는 뜻이 아니다.
- 모델별 중복 후보와 실패를 별도 집계한다. 동일 결과의 재반입·재게시를 새 기획서로 세지 않는다. 선택되지 않은 후보도 보존한다.
- Storyyard에 당일 후보 전체를 올리고 추천 후보를 우선 표시할 수 있다. 사용자는 추천과 무관하게 모두 읽고 판정할 수 있다.
- 모델·경로별 완료 수, 소요 시간, 관측 가능한 사용량, 사람의 채택·보류 이유를 기록한다. 웹의 알 수 없는 토큰·비용은 미확인으로 두며 0으로 채우지 않는다.
- 재시도 횟수와 지출 상한은 자동 운용 전에 정한다. 서비스 한도에 걸리면 완료된 수와 미완료 수를 그대로 보고한다.
- 하루 10개는 운영 목표다. 실행 시각·스케줄러·항시 가동 장치는 별도 확정하며 이번 계획 작성으로 예약을 만들지 않는다.

## 7. 저장과 도구 역할

원문과 파생 분석은 Reference Lab 소유, 신규 기획과 작성 이력은 V3 소유, 공통 경계 계약은 HQ, 검토 화면과 판정은 Storyyard 소유로 둔다. 승인된 기획의 InkOS 적용은 후속 명시적 인계로 처리한다.

외장 저장소에는 큰 원문을 둘 수 있고 현재 입력·결과는 맥미니에서 처리한다. 외장 경로를 모델 지침에 여기저기 하드코딩하지 않고 자료 식별자와 현재 위치를 연결한다. 다른 Windows 컴퓨터의 상시 가동을 기획 검토의 필수 조건으로 만들지 않는다.

Notion에 운영 문서가 필요하면 기존 지정 페이지를 사용한다. ClickUp은 사람의 일정·담당 업무가 생길 때 선택적으로 연결한다. 기획 본문과 HIL 상태를 세 서비스에서 독립 편집하지 않는다.

## 9. 보류·확인 사항

- OpenAI 웹 경로는 ChatGPT 대화 화면으로 정했다. 웹도 모델·모드가 구분될 수 있으므로 실제 계정 화면의 표시를 기록한다. 웹이라는 이유로 단일 범용 모델로 취급하지 않는다. 공식 근거: https://learn.chatgpt.com/docs/models 및 https://learn.chatgpt.com/docs/cloud .
- 각 웹 서비스에서 사용할 모델·모드와 Hermes 연결의 실제 가용성.
- 하루 10개 정기 운용 시각과 재시도·지출 상한.
- 현대판타지 6개 → 판타지 6개 → 무협 6개 순서는 사용자 확정. 현대판타지 주축·보조 원작 묶음은 위 제안과 원문 대조로 구체화하며 기존 보류 변주를 승인된 예시로 쓰지 않는다.

초기 핑 단계에서는 ego-browser 웹 3곳, Hermes Astra, Grok CLI 단독 핑을 실행했다. 이후 연결·카나리·게시 결과는 문서 상단의 후속 보고서가 이 기록을 대체한다.
