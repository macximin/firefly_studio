# 원작 중심 제작을 위한 1차 수정안

2026-09-05 · 구현 계획 · 코드 변경과 신규 생성은 아직 실행하지 않음

## 목표와 완료 범위

**1차 목표는 원작의 재미와 주인공의 자기 이익을 보존한 기획을 만들고, 그 근거를 기존 Storyyard 검토 화면에서 비교할 수 있게 하는 것이다.** 명칭 정리만으로 끝내지 않되 Book·A/B레일·Writer까지 한꺼번에 뜯어고치지는 않는다.

첫 결과는 **원작 기획 복원 1개 → 유지·변경 범위 → 가까운 변주 기획 2개 → 원문 대조 심사 → 사람의 선택**이다. 다른 욕망을 가진 새 전제 두 개를 먼저 발명하지 않는다. 원작 복원이 틀리면 거기서 수정하며 신작 후보로 넘어가지 않는다.

복원 통과는 기존 분석 자료에 원문 대조와 독립 검수 결과를 기록하는 확인이다. 새로운 Human Premise 선택이나 별도 HIL 유형을 추가하지 않는다. 두 신작 기획의 선택은 기존 Storyyard 검토 흐름에서 한다.

기획서는 기존 육하원칙 양식을 쓴다. Book은 작품 관리 단위, 사용자가 말한 아크는 A/B레일 계열의 전개 설계다. Storyyard의 기존 B레일 아크→아크, 회차→블록 대응을 유지한다. InkOS의 `ArcPacket`은 그와 연결되는 상세 실행 입력으로 구별한다.

| 현재 문제 | 수정 후 확인할 결과 |
| --- | --- |
| 돈·소유·승리를 지운 뒤 우정·존중 욕망을 새로 만듦 | 원작의 자기 목표·선택·우위·실제 이득을 먼저 복원하고 같은 중심으로 변주 |
| 작성자에게는 원문이 가지만 심사자는 후보 설명만 읽음 | 작성자와 심사자가 같은 근거 원문을 읽고 서로 독립적으로 판단 |
| 주축 하나를 쓰려 해도 보조 참고작이 필수 | 이 제작 방식에서는 주축 하나만으로 시작 가능 |
| 원작 보존 근거가 기존 사람 전제와 묶여 있음 | 사람 전제를 만들지 않아도 원작 보존 근거를 Storyyard에서 확인 |
| 목격자·관계 변화 등 필수 칸이 장면을 억지로 만듦 | 실제로 없는 요소는 없다고 표현하고, 존재하는 이득과 행동을 심사 |
| A/B라는 이름으로 서로 다른 내용을 설명함 | 실제 A/B레일을 보존하고 피치의 성과·관계 항목과 구분 |

## 1. 변경 범위

**대상은 ‘원작 중심 재설계’를 선택한 새 기획 실행이다.** 아래에서 이 설정을 `source-first`라고 표기하며, 이는 실행 방식을 구별하는 설정이지 사용자에게 추가하는 제작 단계가 아니다. 기존 일반 기획과 과거 Human Premise 실행은 읽을 수 있게 유지한다.

| 순서 | 담당 저장소 | 작업 | 완료 조건 |
| --- | --- | --- | --- |
| 1 | HQ·InkOS | 용어 설명, 기획서·생성·심사 지침의 충돌 정리 | 아크와 ArcPacket, 실제 A/B와 피치의 성과·관계가 혼동되지 않음 |
| 2 | Reference Lab | 주축 하나의 원작 기획·핵심 사건 복원과 분석 오류 정정 | 사실과 해석을 구별하고, 자기 목표·선택·지급을 원문 위치로 확인 |
| 3 | InkOS | 기존 일반 pitch 경로에 원작 우선 실행과 동일 근거 심사 연결 | Human Premise 선행 발명·보조작 의무 없이 두 기획 생성·심사 가능 |
| 4 | InkOS·Storyyard | 원작 근거 전송과 선택적 보상·관계 표현을 공동 수정 | 과거 검토 자료를 유지하면서 새 기획의 원작 근거도 화면에서 읽힘 |
| 5 | 세 저장소 | 실제 원문으로 기획 카나리 1회 | 원작 복원·두 변주·독립 판정·사람 검토까지 확인. Book 생성 전 종료 |

1·2와 계약 상세 검토는 병행할 수 있다. 3·4의 검증을 마친 뒤 5를 실행한다. 이 계획서를 승인한 사실을 새 후보에 대한 선택으로 사용하지 않는다.

## 2. 용어와 기획 기준을 맞추는 수정

- 기존 A레일·B레일·Storyyard 아크·블록 명칭과 ID를 보존한다. `ArcCanvas`에서 상세 실행 입력을 가리키는 ‘현재 Arc’는 `ArcPacket · 1~3화 실행 계획`처럼 기존 코드명과 뜻을 병기한다. 단어 일괄 치환은 하지 않는다.
- 미래 선점 카드의 ‘A레일·실행과 보상’, ‘B레일·저항과 후과’는 카드 내용에 맞는 설명만 남긴다. 이 카드는 실제 A/B레일이 아니다.
- 피치 `railA/railB`는 현재 의미인 성과 누적·관계 변화를 설명한다. 실제 `anchorRail/arcRouteRail`로 간주하거나 자동 복사하지 않는다.
- Markdown 양식과 `webnovel-plan-format.ts`, 실제 사용되는 pitch/review 지침을 같이 수정한다. ‘현재 Arc’는 해당 문맥이 가리키는 A/B 전개, B레일 아크 또는 ArcPacket을 명확히 적는다.
- 원작 복원 이전에 새 결핍·우정·사명·인정 욕망을 확정하는 순서를 바꾼다. 돈·권력·소유를 지워도 남는 대인 욕망을 찾는 조건은 이 새 실행에 적용하지 않는다.

자기중심성의 판단은 **자신의 이득과 목표가 타인의 편의·평가·요구보다 우선하는가**다. 능동적이라는 말만으로 통과시키지 않는다. 투자·보수 지급은 자기 목표를 위한 실제 거래인지 보고, 손해를 ‘마음이 편해짐’으로 사후 합리화하지 않는다. 원작에 희생이나 인정 욕구가 있다면 사실대로 적고 해당 구간의 채택 여부를 따로 판단한다.

## 3. 원작 복원과 입력 구성

첫 검증의 주축 후보는 기존 분석·변형 팩이 있는 **「독식하는 재벌 3세」**다. 전편이 이번 취향을 완벽하게 충족한다고 선인증하지 않는다. 다른 주축이나 보조작을 추가하기 전에 기존 자료가 실제 원문을 제대로 설명하는지 확인한다.

1. 기존 `project_bible.md`, `project_pitch.md`, `chapter_map.csv`, `arc_atlas.md`로 전체 흐름을 확인한다. 원작의 목적을 사용자가 원하는 목적에 맞춰 고쳐 쓰지 않는다.
2. 도입의 연속 사건과 자기 몫을 챙기는 핵심 사건을 완결되는 범위로 읽는다. 초기 검토 범위는 1~10화와 52~53화를 후보로 삼되 실제 사건 경계에서 부족하면 앞뒤를 포함한다. 중후반 목표와 결말 주장은 해당 원문까지 확인하거나 미확인으로 표시한다.
3. 확인된 1화의 ‘이미 사랑받는 손자’를 ‘애정 결핍을 해소하는 손자’로 바꾼 요약 등을 정정한다. `chapter_map`에서 파생되는 story-index도 같은 수정본으로 재생성한다. 원작 본문은 수정하지 않는다.
4. 원작 복원과 취향 적합성 판단을 기존 분석 자료 안에서 구별한다. 전체 재독이 끝나지 않았다면 국소 정정 범위를 명시하고 기존 전수 분석 완료 표시를 새 기준의 전편 인증으로 재사용하지 않는다.
5. 작성자·심사자에게 전체 줄거리의 검수된 개요, 현재 연속 사건 원문, 장기 확장의 근거, 유지·변경 지시를 공급한다. 원문 본문은 기존 private input 경계 안에 둔다.

일반 pitch 입력은 현재 총 400,000바이트 제한이며 Human Premise의 앞 24,000자 절단과 다르다. `arc_atlas.md` 전체를 무작정 넣지 않는다. 파일 크기뿐 아니라 실행 모델의 컨텍스트 여유를 확인하고, 필요한 인과를 끊지 않는 묶음을 준비한다. 넘치면 조용히 앞부분만 잘라 넣지 않고 범위를 다시 구성한다.

원문 해시, 실제 읽은 회차·행 범위, 사용한 분석 수정본을 기존 참고 입력 기록에 남긴다. 원작의 마지막까지 읽지 않은 상태에서 완결 상태를 만들어 넣지 않는다.

수정 위치: [해당 작품 분석](../edge_repos/firefly_reference_lab/analyses/doksik-chaebol3/project_bible.md), [회차 분석](../edge_repos/firefly_reference_lab/analyses/doksik-chaebol3/chapter_map.csv), [파생 팩 생성기](../edge_repos/firefly_reference_lab/tools/build-corpus-reference-pack.mjs), [기존 변형 팩](../edge_repos/firefly_reference_lab/inkos_handoffs/doksik-chaebol3-transformation-pack/v1/README.md).

## 4. 기존 pitch 경로를 원작 우선으로 연결

`pitch slate → review → export-storyyard → 사람 결정`을 재사용한다. 새 노선은 `human-premise → commercial-expansion`을 필수 선행 과정으로 삼지 않는다. 과거 p01 우정안·p02 약혼 거절안은 재사용하지 않고 기존 거절·중단 기록을 보존한다.

| 수정 | 실제 구현 판단 |
| --- | --- |
| 실행 구분 | 새 실행에만 명시적인 원작 우선 설정을 적용하고 slate에 기록. 일반·과거 실행에 자동 소급하지 않음 |
| 생성 순서 | 검토한 원작 복원 결과를 입력으로 사용. 후보 간 차이는 지정한 표면·국소 인과에서 만들고 중심 욕망을 다르게 만들라는 지시를 제거 |
| 주축 하나 허용 | `supportingReferenceRoutes: []` 허용을 새 방식에 한정. 현재 `objectArray` 기본 최소 1개 검사를 수정. 같은 주축을 가짜 보조작으로 다시 넣지 않음 |
| 같은 원문으로 독립 심사 | slate의 참고 경로·해시를 다시 검증하고 생성에 쓴 근거 묶음을 reviewer context에도 전달. 현재 reviewer는 후보와 rubric만 읽는 공백을 수정 |
| 변경 추적 | 실제 변경 요소마다 원작 요소→변경 내용→영향받는 선택·실행·보상·후속 사건을 연결. `preservedSkeleton`과 `linkedCausalAdjustments`를 문구 체크만으로 통과시키지 않음 |
| 의미 판정 | 자기 이득 우선, 원문 보존, 읽는 재미를 별도로 보고. 앞의 두 항목이 깨졌는데 총점이 높다고 SURVIVE로 추천하지 않음 |
| 실패 처리 | 원문 부족·분석 오류·변주 이탈·문장 약화를 구별하고 실패한 단계만 수정. 새 설정이나 새 작품으로 도망가지 않음 |

동일 파일을 읽었다는 사실은 의미 보존의 증거가 아니다. 심사에는 실제 원작의 선택과 후보의 선택을 함께 제시한다. 주인공이 지분 대신 칭찬에 만족하는지, 능력 사용을 줄이고 관계를 얻는 이야기로 바뀌었는지 등을 행동과 결과로 판단한다.

수정 위치: [pitch 명령과 생성·심사 프롬프트](../edge_repos/inkos/packages/cli/src/commands/pitch.ts), 해당 native skill과 rubric. 참고 입력은 기존 `loadReferenceContext`의 텍스트 로딩·해시 계산과 기록을 재사용하고, 리뷰 시 저장된 SHA와 재대조하는 검사를 추가한다. 새 검색 플랫폼을 만들지 않는다.

## 5. InkOS·Storyyard 공동 계약 수정안

**기존 바깥 HIL v3와 결정 흐름을 유지하되, 원작 근거의 새 형식은 안쪽에서 버전을 구별하는 안을 권고한다.** 현재 `spineRetention/v1`의 뜻을 몰래 바꾸거나, 없는 사람 전제를 채워 넣지 않는다. 아래는 새 형식의 설계 범위이며 실제 스키마는 아직 추가하지 않았다.

### 과거 자료와 새 자료의 구별

- 기존 v3 후보·Human Premise·`spineRetention/v1`은 기존 규칙 그대로 읽는다. 저장된 패킷·후보 SHA, 인덱스, 사람 결정을 다시 쓰지 않는다.
- 새 원작 우선 후보에는 `spineRetention`의 안쪽 v2를 사용한다. 양쪽 검증에서 허용하는 조합은 **일반 후보: 둘 다 없음 / 기존 전제 확장: 실제 sourcePremise + spine v1 / 새 원작 우선 후보: sourcePremise 없음 + spine v2**로 제한한다. 전제만 있거나 v1만 있거나 v2에 과거 전제를 붙인 조합은 거절한다. 새 방식에 과거 사람 전제 선택을 꾸며 연결하지 않는다.
- 안쪽 v2는 주축·원문 근거·원작의 자기 목표와 선택·유지 조건·초반 대응·표면 변경과 인과 영향·실제 보상을 담는다. 관계 변화·감정 보상·외부 목격자는 실제 있는 경우만 담는다. 기존 필드를 가능한 한 재사용하고 별도의 대규모 기획 플랫폼을 만들지 않는다.
- Storyyard의 근거 표시 조건도 바꾼다. 현재 `sourcePremise`와 `spineRetention`이 함께 있어야 표시하는 조건을 분리하고, 원작 근거만 있어도 복원 내용·변경 내용·원문 위치를 읽을 수 있게 한다. 원문 전문은 외부 패킷에 넣지 않는다.

비교 화면은 **원작에서 누가 무엇을 원했고 어떻게 자기 몫을 얻었는지 → 후보에서 무엇을 유지·변경했는지**를 실제 인물·사건·물건과 함께 보여 준다. ‘성장·관계·보상’ 같은 추상 태그와 해시만 나열하지 않는다. 원문 위치와 복원 자료는 확인 가능한 근거로 연결하고, 인과 비교에 필요한 파생 설명을 패킷에 담는다.

### 바깥 후보의 강제 항목도 함께 처리

안쪽 v2만 추가해서는 부족하다. 현재 바깥 후보에도 `railB` 최소 3개와 각 `arcLadder.relationshipConversion`이 필수다. 다만 기존 필드로 이미 사실을 표현할 수 있는 항목까지 모두 바꾸지는 않는다.

- **기획 검토용 새 후보 분기**에서는 관계 목록이 없으면 `railB: []`, 검토 결과 특정 전개의 관계 전환이 없으면 `relationshipConversion: null`을 허용한다. 키 자체는 필수다. 누락·빈 문자열·공백 문자열은 미완료로 거절하고 null은 근거와 함께 의미 심사를 받는 ‘해당 없음’으로 처리한다. 과거 후보에는 null을 허용하지 않는다.
- `entryContract.commercialPromise.payoffWitness`는 이번 1차에서 기존 문자열 구조를 유지한다. 이미 실제 지급을 쓰거나 즐기는 행동을 담을 수 있으므로 그 행동을 적고, 구경꾼을 발명하지 않는다. 결핍·모욕이 없는 원작은 없다는 사실과 현재 처지를 명시한다. 실제로 없는 것을 빈칸 회피용 사건으로 채우지 않는다.
- `arcLadder` 최소 6개와 초반 1~4화 범위도 이번 주축의 검증에서는 유지한다. 기존 전편 분석으로 장기 전개를 구성하되 직접 읽은 구간과 분석에 의존한 구간을 구별한다. 계약을 채우려고 미래 사건을 발명해야 한다면 후보를 통과시키지 않고 복원·계약 적합성부터 다시 검토한다. 모든 작품의 아크 수를 여섯 개 이상으로 정한다는 일반론은 아니다.
- 기존 Book 승인용 `FireflyEntryContractSchema`는 유지한다. 새 후보의 Book 승격은 다음 단계의 reference binding·승인 입력 연계가 준비될 때까지 지원하지 않음을 명확히 처리한다. 값이 모두 문자열인 후보라도 원작 우선 실행이면 1차에서 승격하지 않는다.

CLI가 확정하고 slate에 저장한 실행 설정을 생성·review·export·decision·promote에서 이어 쓴다. 실행 설정과 새 후보 근거 버전이 다르면 거절한다. 후보가 v2라는 문자열만 출력했다고 일반 실행의 제약을 해제하지 않으며, 새 방식인데 v1 근거만 남거나 v2 근거가 없으면 조용히 일반 경로로 되돌리지 않는다.

이것은 **새 수신기가 과거와 새 자료를 모두 읽는 호환성**이다. 구 Storyyard가 새 자료를 읽을 수 있다는 뜻은 아니다. 배포 순서는 새 자료를 읽는 Storyyard 검증·렌더러 준비 → InkOS 생산 기능 활성화다. 전송 전 대상 Storyyard의 적용 revision이 새 후보 fixture를 통과한 revision인지 확인한다. 확인되지 않으면 로컬 검토 파일까지만 준비하고 그 대상에는 전송하지 않는다. 바깥 버전 문자열이 v3라는 이유로 지원을 추정하지 않는다.

수정 위치: [원작 보존 스키마](../edge_repos/inkos/packages/core/src/planning/spine-retention.ts), [기획 검토 패킷](../edge_repos/inkos/packages/core/src/storyyard/pitch-review-packet.ts), [Storyyard 검증](../edge_repos/storyyard/app/firefly-review-contract.ts), [Storyyard 검토 화면](../edge_repos/storyyard/app/review/review-board.tsx). `pitch.ts`의 후보 검증·Markdown 렌더링·선택 기획 출력·내보내기도 새 기획 분기를 읽도록 함께 바꾼다. `renderEntryPlan`과 [기존 기획 입력 계약](../edge_repos/inkos/packages/core/src/planning/entry-contract.ts)은 보존한 문자열 구조로 작동하는지 회귀 확인한다. 기존 `payoffPair`만 출력해 새 보상 자료가 누락되는 경로를 남기지 않는다.

기존 정본의 `mappingVersion`, `arcUnit`, `blockUnit`, `bId`, `kind: act`는 변경하지 않는다. 1~3화와 기존 정본 화면의 1~5화 차이도 이번 기획 계약 개정으로 통일하지 않는다.

## 6. 검증과 첫 카나리

| 검증 종류 | 확인할 것 |
| --- | --- |
| 원문·분석 | 알려진 오독 정정, 해당 chapter_map→인덱스 반영, 원문 불변, 읽은 범위와 주장 범위 일치 |
| 생성·심사 입력 | 원작 우선 실행만 주축 1개 허용. 작성자·심사자 모두 같은 검수된 근거를 받으며 파일이 바뀌면 오래된 해시로 진행하지 않음 |
| 계약 회귀 | 과거 v3/v4와 spine v1 자료·해시·결정이 유효. 새 spine v2는 사람 전제 없이 통과. 잘못된 결속·변조 해시·부재와 누락 혼동은 거절 |
| 실제 표시 | 원작 근거만 있는 후보도 Storyyard에 표시. null 관계 항목·실제 보상·향유 행동을 렌더링해도 오류나 가짜 내용 없음. 기존 정본 아크·블록 대응 보존 |
| 추천 판단 | 원작의 자기 이득을 칭찬·우정·타인 구제로 대체한 후보를 높은 총점 때문에 추천하지 않음. 거래 비용·원작의 실제 희생은 사실대로 구별 |
| 종료 경계 | 새 원작 우선 기획의 사람 선택은 남길 수 있지만 미지원 Book 승격·ArcPacket·원고 생성으로 이어지지 않음 |

기존 테스트를 중심으로 확장한다: InkOS `pitch-command.test.ts`, `planning-entry-contract.test.ts`, `webnovel-plan-format.test.ts`와 원작 보존/검토 패킷 테스트, Storyyard `firefly-review-v3.test.mjs`, `firefly-review-v4.test.mjs`, `firefly-review-batch.test.mjs`, Reference Lab `build-corpus-reference-pack.test.mjs`. 실제 변경 패키지의 빌드·타입 검사를 포함한다. 화면 설명만 바꾼 곳에는 문자열을 그대로 되풀이하는 새 테스트를 늘리지 않는다.

양쪽이 별도로 만든 fixture만 통과시키지 않고 **InkOS에서 만든 같은 패킷을 Storyyard 검증기에 넣는 검사**를 둔다. 현재 InkOS 단위 fixture에는 `artifact.id`와 `source.slateId`가 다른 예가 있지만 Storyyard는 같아야 한다고 검증한다. 실제 export와 동일한 ID 대응으로 검사를 통일하고 잘못된 대응의 거절을 양쪽에서 확인한다.

실제 카나리에서는 모델·원문·분량을 고정하고 방법만 바꾼다. 주축 원작 복원이 먼저 통과해야 같은 중심의 가까운 변주 2개를 만든다. 원문·복원·두 기획의 차이를 한 비교 자료로 보여 주고 사람 선택을 받는다. 기존에 중단한 카나리 ID나 결정을 덮어쓰지 않는다.

**1차 완료는 ‘기획 단계에서 원작의 목적과 재미를 보존했는가’를 검증한 상태다.** 원고 품질, 장편 지속성, 흥행을 검증했다고 보고하지 않는다. 두 기획 모두 틀리면 새 전제 발명이 아니라 오류가 난 복원·변주 단계를 고친다.

## 7. 다음 차수로 넘길 작업

- 선택 기획의 원작 binding·변형 지도를 Book에 설치하고 A/B레일과 연결하는 작업.
- 진행률로 원문 세 회차를 고르는 fallback을 이 제작 방식에서 없애고, 실제 사건 대응으로 ArcPacket·Writer 입력을 구성하는 작업.
- 선택→승부→지급이 끝나는 사건 묶음의 짧은 원고 검증. 한 묶음이 길면 여러 ArcPacket으로 구현한다.
- InkOS의 A/B레일을 Storyyard 기존 플롯에 연결하는 새 어댑터. 기존 Foundry 정본 경로와 별도로 검증한다.
- 보조 원작 조합, 대량 생성, 모델 교체 비교, 문체 다듬기 스킬 추가.

이 항목들은 필요 없어서 제외한 것이 아니다. 첫 기획의 동기부터 틀리는 상태에서 동시에 바꾸면 무엇이 개선됐는지 구별할 수 없으므로 순서를 나눈다. 기존 pitch/review 스킬부터 수정하며, 일반적인 ‘AI 문체 제거’ 스킬을 자기중심성·원문 보존 문제의 해결책으로 두지 않는다.

## 판단 근거와 검토 상태

[원작 중심 재설계 조사](2026-09-05-source-first-redesign-methodology.md)와 [InkOS·Storyyard 계약 대조](2026-09-05-inkos-storyyard-terminology-contract-audit.md)를 기반으로 실제 코드 경로를 재확인했다. 독립 조사에서 심사자의 원문 미수신, 보조작 필수, spineRetention·sourcePremise 결속, 화면의 동시 존재 조건을 추가로 확인했다.

검토한 작은 대안은 ‘기존 v3를 전혀 바꾸지 않고 로컬 Markdown 근거를 따로 열어 검토’였다. 코드 변경량은 줄지만 Storyyard 안에서 원작 근거를 함께 확인하지 못하는 공백이 남는다. 따라서 이번 권고는 한정된 공동 계약 수정을 1차에 포함한다. 새 플랫폼·전체 데이터 마이그레이션·전면 개명은 필요하지 않다.

초안 검토 뒤에는 바깥 기획 항목의 완화 범위를 줄였다. `payoffWitness`는 기존의 향유 행동 표현을 쓰고, 장기 전개 최소 수는 이번 장편 주축의 기존 분석으로 확인한다. 1차 구조 변경은 실제 부재를 표현하지 못하는 관계 항목과 원작 근거 전달에 집중한다. 또 실행 설정·근거 버전의 일치, 허용하는 전제/근거 조합, 같은 패킷의 양쪽 검증, 전체 렌더링 경로를 명시했다.

계획 검증 기록과 독립 검토 반영 결과는 [증거 파일](evidence/2026-09-05-first-revision-plan.json)에 남긴다. 실행 성과는 후속 구현과 실제 카나리에서 확인해야 한다.
