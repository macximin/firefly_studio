# V3 · Storyyard 호환 점검과 Hermes 기획 전문가 구성안

2026-09-06. 사용자 의도는 **Hermes 안에 Grok·Astra medium 등 역할별 전문가를 배치해, 현재 Storyyard에서 읽고 판단할 기획서와 A/B레일 구조도 양식을 확정하는 것**이다. Codex 하위 에이전트 모집으로 해석하지 않는다.

결론: 기존 연결을 활용할 수 있다. 다만 V3의 옛 승인 원고 투영 경로를 그대로 새 기획 HIL에 연결할 수는 없다. 기획서는 합의한 9절을 유지하고, A/B레일의 의미와 표시·판정 방식을 맞추는 작업이 필요하다.

## 실제 옛 export 시험

현재 Storyyard exporter에 복원된 V3 경로를 명시해 6작품을 별도 로컬 출력 폴더로 변환했다.

- `isekai_restaurant`: 통과. `firefly_story_package_v1`, 아크 4개·블록 3개.
- `afterlife_restaurant`: 승인된 도입 이력과 연결되지 않은 회차 약속 검사에서 중단.
- 나머지 4작품: exporter가 읽은 원고와 manifest 해시 불일치로 중단.

이는 복원본 전체가 손상됐다는 판정이 아니다. exporter의 하드코딩된 원고 파일 선택과 승인된 revision의 차이 등을 별도로 구분해야 한다. 과거 작품을 지금 고치거나 재승인하지 않았다. 이번 목적은 새 기획 양식의 호환성 확인이며 옛 6작품 전량 수리로 확장하지 않는다.

실행 결과: `.firefly/v3-storyyard-compatibility-20260906/legacy-export-check.json`.

## Hermes 전문가 구성 제안

아래는 역할 배치안이다. 특정 모델의 우월성을 검증한 결과나 이미 생성·실행된 프로필 목록은 아니다.

| 역할 | 모델 제안 | 책임과 결과 |
| --- | --- | --- |
| 원작 역설계·소재 편집 | Grok | 실제 원문에서 탐나는 대상·자기 이득·구체 쾌감을 찾아 비교. 추상 기능만 남기고 다른 소재를 임의로 끼우지 않도록 근거 제시 |
| 기획서 편집 | Astra medium | 선택한 원문·소재를 동일한 9절 기획서로 작성. WHO/WHAT/HOW/WHERE/WHEN/WHY와 장기·단기 목적 연결 |
| A/B레일 설계 | Astra medium, 별도 프로필 | 기획의 장기 도착점과 사건 경로·선택·보상·다음 목적을 구조화. 가까운 구간만 상세화 |
| 독립 상업성 검토 | 작성자와 다른 모델 레인 또는 사람 | 자기평가를 보지 않고 재미와 소재 선택을 비교. 처음부터 모델을 더 늘리기보다 결과를 보고 추가 후보 선정 |

관리·호환 담당은 결과를 현재 Storyyard 형식으로 변환하고 원문·기획서·아크·HIL의 버전을 연결한다. 모델이 많다는 이유로 다수결하거나 문장을 평균내지 않는다. 작성 결과를 비교해 사람의 판단으로 채택한다.

현재 Hermes 설치에는 named profile, `openai-codex`, `xai-oauth` 실행 코드가 있다. Firefly의 기존 InkOS 프로필은 Astra **high**이며 high를 전제로 하는 검증도 존재한다. 따라서 V3 기획용 medium 프로필을 별도로 구성하는 편이 맞다. 현재 `firefly-studio` 일반 프로필은 Terra medium으로 확인됐다. 이를 기존 InkOS 작성 프로필과 혼동하지 않는다.

Grok CLI도 설치돼 있으나 이것만으로 Hermes의 Grok 연결이 성공했다고 주장할 수 없다. 실제 인증·모델 사용 가능 여부는 프로필 설정 후 짧은 호출로 확인한다. 이번 점검에서는 인증 갱신, 모델 호출, 프로필 변경, 자동화 시작을 하지 않았다.

## 확정할 양식

**기획서:** 기존 `docs/templates/webnovel-project-plan-v1.md`의 1~9절과 육하원칙을 그대로 사용한다. V3의 시작·지속 증명은 그 안에 담는다. 원문 근거·검토 기록은 본문을 가리지 않게 별도 보관한다. 모든 모델이 동일한 양식을 사용한다.

**A/B레일 구조도:** 위에는 A레일의 장기 도착점을, 아래에는 해당 A에 속한 B레일의 사건 경로를 표시한다. 아크 카드를 열면 다음을 읽을 수 있어야 한다.

- 진입 상황과 주인공의 현재 목적.
- 선택·우위 사용·사건의 진행.
- 주인공이 실제로 얻는 것과 독자가 즐길 구체 장면.
- 끝 상태와 다음 아크가 가능한 이유.
- 예상 회차 범위, 상위 A 연결, 현재/다음/먼 가설 상태.

기계 연결에는 기존 ID와 순서·상위 관계를 사용한다. 필드를 늘리기 전에 V3와 InkOS의 기존 대응 필드를 비교한다. 아크 카드가 바뀌면 연결된 기획·집필 입력 중 무엇을 다시 봐야 하는지 확인할 수 있어야 한다. 이전 기획서의 승인으로 이후에 바뀐 아크까지 승인된 것으로 처리하지 않는다.

## 권장 진행 순서와 완료 기준

1. 현재 9절 기획서와 A/B레일 구조도 대응표를 공통 작업 지침으로 고정한다.
2. Hermes의 기획 전문가 프로필과 공통 입력을 구성한다. 합의한 양식·실제 원문·사람이 채택/보류한 예시를 매 작업 입력에서 읽게 한다. HIL을 파일에 저장한 것만으로 다음 호출이 학습했다고 취급하지 않는다.
3. 같은 자료로 기획서와 가까운 첫 아크를 작성·비교한다. 원작에서 재미있었던 구체 대상과 선택이 변주에서도 살아 있는지 사람이 판단한다.
4. 현재 Storyyard에서 전문과 구조도를 열어 같은 후보를 판단할 수 있게 한다. 원고 없이도 검토할 수 있어야 하며 기존 9절·육하원칙이 사라지지 않아야 한다.
5. 채택한 기획·아크를 InkOS 입력으로 변환해 1~3화 집필을 시험한다. 이 단계에서 실제 집필 품질을 별도로 판단한다.

이 문서는 점검 결과와 구성안이다. 전문가 배치·양식 개정·HIL 계약 확장·배포·InkOS 집필이 이미 완료됐다는 뜻은 아니다.
