# 웹소설 인간 작가 아젠다: 구현 계획

2026-09-12 KST · 상태: **계획 수립 완료 / 구현·집필 실험·운영 적용 전**

지금까지 이 아젠다에서 한 일은 외부 자료 조사, 내부 원고 표본 분석, 판단 카드 작성이다. 그 결과를 제작 코드나 운영 프롬프트에 적용하지 않았다. 이번에는 자료 수집을 멈추고, 기존 기능에 작가의 선택과 퇴고 방식을 연결하는 구현 순서를 정한다. 이 문서를 저장한 것은 구현이나 원고 생성의 실행 기록이 아니다.

## 1. 만들려는 변화

**읽고 싶은 장면을 고르고, 인물의 계산으로 그 장면을 움직이며, 초고를 읽은 뒤 필요한 곳을 고치는 집필 흐름**을 만든다. 설명이 그럴듯한 기획서나 작법 항목을 모두 채운 원고가 목표는 아니다.

사용자가 보는 기본 흐름은 기존의 **기획서 → Arc → 원고**를 유지한다. 내부에서 참고 자료와 짧은 선택 기록을 붙이고, 원고에는 실제 행동·대사·내면·보상의 차이가 나타나야 한다. 모든 회차에 열 가지 질문, 여러 후보, 새 에이전트를 강제로 추가하지 않는다.

| 가져올 판단 | 구현에서 달라져야 할 행동 | 잘못 적용한 경우 |
|---|---|---|
| 나비계곡: 어색한 전개를 계획 때문에 붙잡지 않기 | 이미 쓴 사실과 작품의 매력을 지키면서 아직 쓰지 않은 경로를 수정 후보로 제시 | 확정된 사실을 즉흥적으로 바꾸거나 현재 Rail 제약을 무시 |
| 나비계곡: 결단을 납득시키는 내면 | 위험을 알면서도 행동하는 이유가 필요한 장면에서 망설임·계산·결단을 남김 | 내면을 전부 삭제하거나 모든 행동에 감정 해설 추가 |
| 나비계곡: 독자 반응의 위치 구분 | 어디까지 읽은 사람의 어떤 불만인지 기록하고 수정 이유와 연결 | 최신 댓글만 항상 옳다고 간주하거나 초반 이해 실패를 취향 탓으로 처리 |
| 조건상·서오·강동호 표본: 서로 다른 속셈 | 같은 정보를 받아도 인물마다 다른 목적·오해·발화·행동이 나오게 함 | 조연이 주인공을 칭찬하거나 설명을 받기 위해서만 존재 |
| 내부 원고 표본: 이긴 뒤의 삶 | 돈·지위·접근권·관계 변화가 다음 선택과 생활에서 드러나게 함 | 계약 과정과 큰 수익 숫자만 늘림 |
| 기존 에셋: 결함을 먼저 찾는 퇴고 | 장면 선택, 정보 공개, 인물 의도, 목소리 중 무엇을 고칠지 정한 뒤 수정 | 매끈하게 압축하는 것 자체를 개선으로 간주 |

나비계곡 관련 근거는 [이미 읽은 공개 인터뷰를 정리한 보고서](2026-09-11-korean-webnovelist-mind-supplement.md)다. 이번 조사에서 나비계곡의 소설 원문을 분석한 것은 아니다. 그의 방법 전부를 기본값으로 채택하거나 특정 작가의 문체를 재현했다고 주장하지 않는다. 적용 질문은 [판단 카드](korean-webnovelist-decision-cards.md), 장면 근거는 [초기 원고 분석](../edge_repos/firefly_reference_lab/comparisons/2026-09-11-author-thinking-and-prose.md)과 [중·후반 분석](../edge_repos/firefly_reference_lab/comparisons/2026-09-11-author-craft-mid-late.md)에 둔다.

## 2. 현재 구현에서 재사용할 것

다음은 2026-09-12 로컬 체크아웃을 읽어 확인한 내용이다. 실행 시험 결과나 원격 최신 상태를 뜻하지 않는다. 기준 커밋과 파일 해시는 [계획 기준 기록](evidence/2026-09-12-human-webnovelist-plan-baseline.json)에 저장한다.

| 영역 | 현재 코드에서 확인한 것 | 이번 계획의 보강 지점 |
|---|---|---|
| 일일 기획 | HQ `scripts/planning-input.py`·`daily-planning.py`가 입력·실행·형식 검사를 맡고 Foundry에 결과 저장 | 선택한 장면 근거와 판단 자료를 선택적으로 입력에 연결 |
| 기획의 참고 원문 | `load_source_materials()`가 원문 앞 7,000자와 분석을 사용 | 다른 위치의 장면도 기능과 선택 이유를 붙여 공급. 기존 입력은 비교 기준으로 보존 |
| 회차 의도 | InkOS `models/input-governance.ts`에 `ChapterMemo`·`ChapterIntent`·`ContextPackage` 존재 | 기존 `goal`, `body`, `mustKeep`, `mustAvoid`, 선택 문맥을 활용. 같은 뜻의 필드를 중복 신설하지 않음 |
| 집필 | `agents/writer-prompts.ts`에 독자 재미, 목적·행동·반응·보상, 상대 이해관계, 지식 경계가 이미 있음 | 추상 규칙을 늘리기보다 해당 장면의 근거와 선택에 연결 |
| 작법 입력 | `production/production-skill.ts`가 선택한 Skill과 자원 파일의 해시를 기록. `production-kernel.ts`가 `activatedSkills`를 해석 | 기존 선택형 입력을 이용해 작은 작법 묶음을 실험. 필수 `inkos-long-writing`은 유지 |
| 퇴고 | `agents/reviser.ts`에 명시적 수정 지시와 advisory issue 검토 경로 존재 | 수정 전 결함과 보존할 장점을 기록하고 기존 후보 수정 경로에 전달 |
| 자동 검토 | `pipeline/chapter-review-cycle.ts`가 critical issue 중심으로 자동 수정 | 작법상 취향 차이를 새 critical 판정으로 바꾸지 않음 |
| 미래 전개 | `arc/rail-context.ts`·`arc/reflow-schema.ts`에 현재·다음 구간과 미래 B-Rail 수정 근거 존재 | 실제 원고에서 생긴 변화로 아직 쓰지 않은 경로를 재검토 |
| 비교 평가 | 기존 blind-pair는 neutral/Soul 전용이며 schema와 CLI가 두 종류에 묶여 있음 | 일반 작법 적용 전후 비교에 맞는 별도 study 계약 필요. 기존 기능을 이름만 바꿔 재사용할 수 없음 |

기획의 실제 경로와 생산 입장은 [현재 기획 정책](pitch-policy-status.md)을 따른다. **일일 기획 결과를 InkOS Book으로 넘기는 입력 어댑터는 아직 없다.** 이 계획의 원고 실험은 기존 입장을 충족한 격리 시험 Book을 대상으로 설계한다. 이전 기획 결과나 Storyyard의 선택을 원고 생성 권한으로 간주하지 않는다.

## 3. 첫 구현: 짧은 작법 묶음을 선택해서 연결

제안 계약 이름은 `author-craft-pack/v1`, 실행용 Skill 후보 ID는 `korean-author-craft`로 한다. 아래 경로와 계약은 **신규 제안**이며 현재 존재하는 기능 이름이 아니다.

### 자료의 소유와 구성

- HQ: `docs/contracts/author-craft-pack-v1.md`에 전달 계약·상태·권한을 정의한다.
- Reference Lab: `craft_packs/korean-author-craft/v1/`에 분석에서 도출한 자료와 근거 목록을 둔다. 인물 판단, 결단의 내면, 보상 후 생활 등 기능별로 구성한다.
- InkOS: `packages/core/src/reference/author-craft-pack.ts`에서 명시적으로 선택된 자료를 검사하고 실행 입력으로 만드는 어댑터를 구현한다. 분석 콘텐츠의 원본 소유권은 Reference Lab에 둔다.
- 실행 시 기존 Skill 검색 경로 안에 작은 묶음을 물질화하고 `activatedSkills`로 선택한다. 사용자 전역 Skill이나 모든 Book의 기본값을 바꾸지 않는다.

묶음에는 다음을 담는다.

| 항목 | 내용 |
|---|---|
| 신원 | schema version, pack ID, revision, manifest·자원 SHA-256 |
| 범위 | 이번 작업의 단계와 장면 문제, 선택한 카드 ID, 적용 이유 |
| 근거 | 보고서/분석 경로, 원문 식별자·해시·읽은 구간, 관찰과 연구 해석의 구분 |
| 집필 참고 | 보려는 순간, 인물의 사적 목적과 지식 차이, 보존할 목소리를 짧게 기술 |
| 퇴고 참고 | 수정이 필요할 때의 결함 위치, 바꾸려는 효과, 유지할 장점 |
| 권한 | 창작 참고이며 Book 규칙·정사·사람 승인으로 승격되지 않는다는 범위 |

예를 들어 회차 목표는 기존 `ChapterMemo.goal`의 길이 제한을 지키고, 구체적인 선택 이유는 `body`나 선택 문맥에 둔다. 카드 열 개를 필수 입력 필드로 만들지 않는다. 예시 선택 기록은 “상대가 왜 거래를 받아들이는지 보이지 않아, 거래 전에 상대의 급한 사정을 행동으로 드러낸다” 정도로 충분하다. 내부 추론 전문을 요구하지 않는다.

**현재 Skill 로더는 자원 파일 전부를 프롬프트에 펼친다.** 따라서 연구 폴더 전체를 설치하면 안 된다. 선택된 짧은 자료만 실행 묶음에 넣고, 실제 주입 내용과 크기를 확인한다. 원문 전체·비공개 원고를 공개 Git에 복사하지 않으며, 런타임에서 원문이 필요하면 기존 접근 가능한 저장 위치와 검증된 참조를 사용한다.

또한 이 입력은 생산 실행 문맥의 여러 모델 호출에 들어갈 수 있다. 첫 실험은 **작법 묶음을 켠 생산 흐름 전체의 효과**로 해석한다. writer에만 적용했다고 주장하지 않는다. 단계별 효과를 따로 보려면 실제 주입 범위를 분리하고 그 입력 해시까지 기록하는 후속 변경이 필요하다.

### 이미 만든 에셋을 쓰는 방식

[에셋 조사](2026-09-11-human-webnovelist-assets-research.md)의 고정 커밋에서 필요한 원리만 선별한다.

| 자료 | 먼저 가져올 부분 | 제외할 부분 |
|---|---|---|
| wgwtest/novel-writing | 관찰·해석·의도·발화 연결, 인과, 목소리 보존 | 모든 장면에 분석표를 강제하는 사용법 |
| haowjy/creative-writing-skills | 기능별 짧은 문체 참고 파일, 구체적인 실패 사례 | 합성 독자의 반응을 실제 독자 평가로 취급 |
| MJbae/awesome-novel-studio | 같은 사건에서 인물별 계산과 말이 달라지는 대화 참고 | 장면 수·독백 횟수·직접 설명 금지 등의 일괄 제한 |

초기 묶음은 자체 작성한 짧은 적용 설명과 출처를 중심으로 만든다. 실제 파일을 복사하는 경우 조사에 기록된 고정 커밋의 LICENSE·NOTICE와 대상 파일 조건을 다시 확인하고 고지를 보존한다. 새 집필 앱 전체 도입, 자체 RLHF, 자동 커밋·리셋을 포함하는 외부 워크플로 설치는 이 구현에 필요하지 않다.

### 첫 작업 묶음의 완료 조건

1. 같은 입력에서 기능을 끄면 기존 실행 입력과 동작이 유지된다.
2. 선택한 자료만 들어가고, 잘못된 참조·변경된 해시·중복 Skill 충돌을 거부한다.
3. 자료는 창작 참고로 전달되고 owner-confirmed 지시나 Book hard rule로 둔갑하지 않는다.
4. 필수 Skill과 생산 입장 검사가 유지되며, 분석 자료가 Book 내용을 직접 수정하지 않는다.
5. 검증 가능한 입력 묶음과 테스트까지 완성한다. 이 단계만으로 원고 품질 향상을 선언하지 않는다.

## 4. 초고와 퇴고에 연결할 순서

### 4.1 회차 선택과 초고

기존 Planner의 인물·갈등 문맥과 `ChapterMemo`를 활용해, 막힌 부분에 필요한 참고만 고른다. 단순한 장면은 바로 쓰고, 전개가 어색하거나 선택지가 실제로 갈릴 때만 다른 행동·정보 공개 순서를 짧게 비교한다.

Writer에는 해당 장면의 목적과 보존할 특성을 전달한다. 특히 주인공의 이득·욕심·체면을 무조건 이타심으로 순화하지 않는다. 조연도 자기 사정 때문에 움직이게 하고, 독자가 기다리는 구체적인 순간이 본문에서 일어나도록 한다.

기존 프롬프트에는 초반 회차별 보상 배치, 비유 횟수 등 고정 처방도 있다. 첫 실험은 그 위에 모순되는 지시를 덧붙이지 않는다. 우선 양립 가능한 판단 자료로 시작한다. 특정 처방 때문에 관찰한 장점이 사라지는 사례가 확인되면 `writer-prompts.ts`에서 **선택형 프로필 분기**로 해당 문장만 조정하고 별도 비교한다. 기본 프롬프트의 광범위한 교체는 피한다.

### 4.2 읽기와 수정

초고를 남긴 뒤 “무엇이 어색한가 → 무엇을 바꾸면 어떤 독서 경험이 나아지는가 → 무엇은 남겨야 하는가”를 짧게 기록한다. `ReviserAgent`의 명시적 수정 지시·기존 후보 저장 경로를 사용한다.

수정 기록의 예시는 다음과 같다.

- 대상: 상대가 갑자기 호의적으로 변하는 대화 구간.
- 이유: 상대가 얻을 이득이 본문에서 보이지 않아 합의가 작가 편의처럼 읽힘.
- 변경: 상대가 자기 이익을 확인한 다음 조건을 제안하도록 순서를 수정.
- 보존: 주인공의 속물적인 농담과 위험을 계산하는 독백.
- 확인: 수정 전후의 대화에서 상대의 선택이 납득되는지 사람이 비교.

자동 검토의 구조 오류와 창작상 불만은 구분한다. 작법 카드를 만족하지 않았다는 이유로 자동 재작성 루프를 만들지 않는다. 명시적 창작 수정은 한 번의 제한된 후보 생성부터 시작하고, 원본·수정본·변경 이유를 모두 보존한다. 추가 수정 횟수와 비용은 실험 설정에 기록한다.

## 5. 사람 비교로 확인한 뒤 적용 범위를 넓힌다

첫 실험에서는 새 원고 세 쌍을 제안한다. 이는 작은 탐색 실험이며 한국 웹소설 전체를 대표하는 표본이나 고정된 합격 기준이 아니다.

| 시험 장면 | 구별하려는 개선 |
|---|---|
| 서로 다른 속셈을 가진 협상·대화 | 정보의 출처와 오해가 행동·말에 실제로 반영되는가 |
| 손해나 위험을 알고도 행동하는 결단 | 내면이 선택을 납득시키며 긴장을 유지하는가 |
| 이미 이긴 인물의 생활·관계·다음 욕망 | 보상이 체감되고 다음에 볼 일이 생기는가 |

기존 입장을 충족한 격리 Book/시험 fixture에서 같은 기획·직전 정사·모델·설정·분량 조건으로 기본형과 적용형을 만든다. 반복을 지원하는 설정은 고정하고 실제 값과 호출·토큰·비용을 기록한다. 원문 장면을 그대로 재작성해 유사성을 점수로 삼지 않는다.

처음에는 **작법 묶음 유무**만 비교한다. 다음 실험에서 기본형과 적용형 모두 같은 추가 수정 예산을 주고, 수정 지시 방식의 차이를 비교한다. 적용형만 여러 번 다시 써서 이긴 결과를 첫 초고 개선으로 보고하지 않는다. 생성 결과를 보고 좋은 쌍만 고르지 않으며 실패·중단 사례도 남긴다.

평가는 다음 순서로 받는다.

1. 변형 이름과 모델 평가를 숨긴 A/B 원고를 사람이 먼저 읽는다. 표시 순서는 무작위로 정하고 매핑은 별도 보관한다.
2. 다음 장면을 더 읽고 싶은 쪽, 건너뛴 위치, 사람의 말·행동처럼 느껴지지 않은 위치를 먼저 기록한다. 동률·둘 다 별로도 허용한다.
3. 그 뒤 인물 계산, 결단의 내면, 보상 체감, 목소리 보존과 수정 전후를 본문 위치에 연결해 확인한다.
4. 사람 답변을 저장한 뒤 모델 진단과 구현 변형을 공개한다. 모델의 독자 시뮬레이션은 보조 진단으로 분리한다.

### 기존 Storyyard 비교와의 차이

InkOS `storyyard/blind-pair-materialization.ts`와 CLI `review prepare-blind-pair`는 **neutral/Soul 전용**이다. Storyyard `app/firefly-review-contract.ts`의 엄격한 v2 계약도 그대로는 일반 작법 실험을 받지 않는다. 기존 review 화면에는 모델 권고가 보여 사람의 최초 반응을 유도할 수 있다.

따라서 신규 `author-craft-study/v1` 계약을 HQ에 정의하고, InkOS의 생성·검증 어댑터와 Storyyard의 별도 packet 처리·첫 읽기 화면을 양쪽에서 구현한다. 기존 neutral/Soul 계약과 CLI는 유지한다. 기존 원고 표시·선택 컴포넌트는 재사용하되, 변형 정보와 모델 권고를 응답 전 숨기는 동작을 검증한다.

그 UI가 준비되기 전이라면 동일 계약으로 봉인한 로컬 A/B 패킷과 수동 사람 응답 기록을 먼저 사용할 수 있다. 이 경우 Storyyard 연동이 완료되었다고 표시하지 않는다. `humanBlindComparisonPerformed`는 실제 사람이 평가하기 전까지 `false`다.

### 채택 판단

자료 연결·형식·테스트 통과는 기술 완료다. 첫 사람 비교는 유망한지 알아보는 단계다. 원고의 구체적인 개선이 확인되고, 재미·목소리·연속성 손상이 없는지 다른 장면과 연속 회차에서 재확인한 뒤 해당 작품의 선택형 기능으로 채택을 검토한다. 작은 표본의 승률이나 모델 점수 하나로 전체 작품의 기본값을 바꾸지 않는다.

사용자 반응은 `읽은 범위 / 본문 위치 / 실제 발언 / 이해·약속·취향의 문제 / 수정 여부와 이유`로 남긴다. 이 구조는 피드백 근거를 보존하는 용도이며 댓글을 자동 수집하거나 원고를 자동 변경하는 정책은 아니다.

## 6. 후속 연결: 기획과 유연한 미래 전개

### 일일 기획

초기 원고 실험에서 유용한 판단을 추린 뒤 HQ `planning-input.py`에 선택형 작법 묶음 인자를 붙인다. 기존 아홉 항목 기획서와 기존 provider 실행 경로를 유지하고, 앞부분 원문만 사용한 입력과 선택 장면을 추가한 입력을 별도로 비교한다.

Reference Lab이 “이 소재를 쓰라”는 요약만 보내지 않고 **어떤 조건에서 인물이 행동하고 독자가 무엇을 기다리며 무엇을 얻는 장면인지**를 전달하게 한다. 산출물은 현행대로 Foundry에 저장한다. 현행 HQ의 기획 로직을 전부 이관하는 작업은 이번 작은 구현의 선행 조건으로 삼지 않는다.

일일 기획 → InkOS 연결은 별도 전달 계약과 검증 작업이다. source-first Book 입장의 미구현 매핑을 그대로 남겨 둔 채 우회하지 않는다. 스케줄러 재가동, 이전 작품 재개, 신규 Book 생성은 이 계획 저장에 포함되지 않는다.

### 나비계곡식 유연성의 적용 범위

현재 준비된 Rail은 6~12개 anchor와 결말까지의 경로를 요구한다. reflow의 anchor 결정은 현재 `keep`이며 B-Rail의 미래 경로에는 수정·폐기 후보를 표현할 수 있다. 따라서 첫 적용은 다음 범위다.

1. 실제 원고에서 달라진 관계·욕망·독자 기대를 기존 closeout/reflow 근거로 기록한다.
2. 승인된 원고와 확정 anchor를 보존한다.
3. 아직 쓰지 않은 B-Rail 경로를 유지할지, 고칠지, 폐기할지 후보로 만든다.
4. 기존 적용·검증 경로를 거쳐 반영하고 이전 계획과 이유를 남긴다.

**결말 자체를 비워 두는 집필 모드는 별도의 Rail 계약 변경이 필요하다.** 나비계곡을 좋아한다는 의견만으로 현행 준비 조건을 제거하지 않는다. 미래 경로 수정만으로 얻기 어려운 이점이 실제 실험에서 확인되면, 그때 열린 결말 모드의 입장·연속성·회수 규칙을 별도 설계한다.

## 7. 작업 순서와 검증

| 순서 | 구현 단위 | 소유 | 완료를 판단할 산출물 |
|---|---|---|---|
| 1 | 작법 묶음 계약, 기능별 자료, 선택형 해석·입력 | HQ / Reference Lab / InkOS 각각 | 출처 있는 작은 묶음, 입력 receipt, off 상태 호환성 시험 |
| 2 | 기존 Memo·Writer·Reviser 연결, 짧은 선택·수정 기록 | InkOS | 격리 fixture의 입력·초고·수정 후보와 변경 이유. 자동 게이트 보존 |
| 3 | 일반 작법 A/B 계약과 사람 평가 | HQ / InkOS / Storyyard 각각 | 최초 반응이 가려진 비교 자료, 실제 사람 응답, 실패를 포함한 비교 기록 |
| 4 | 효과가 있던 판단의 기획 입력·미래 B-Rail 연결 | HQ / Reference Lab / Foundry / InkOS 각 경계 | 기존 형식과 정사 유지, 선택 장면 근거, 미래 계획 수정 이력 |

**첫 코딩 범위는 1번**이다. 먼저 자료와 입력을 작게 연결하고 호환성을 확인한다. 새 작법 규칙을 기본값으로 배포한 뒤 품질을 알아보는 순서로 진행하지 않는다.

구현 시 확인할 기존 테스트 지점은 다음과 같다. 이번 계획 작성에서는 아래 실행 테스트를 돌리지 않았다.

- `production-skill-phase4.test.ts`, `production-direction-context.test.ts`: 선택/비선택, 해시 불일치, 필수 Skill 보존, 참고 자료의 권한.
- `chapter-memo-parser.test.ts`, `planner-prompts.test.ts`, `writer-prompts.test.ts`, `writer.test.ts`: 기존 입력 호환, 인물·지식 경계, 내면·목소리의 불필요한 삭제 방지. 생성 품질은 별도 사람 평가.
- `chapter-review-cycle.test.ts`, `reviser.test.ts`: advisory가 자동 critical로 바뀌지 않음, 수정 대상·보존 조건, 원본과 후보 분리.
- `canary-isolation.test.ts`: 시험 후 기존 Book 정사·승인 상태·운영 파일이 바뀌지 않음.
- `blind-pair-materialization.test.ts`, `storyyard-review-packet-v2.test.ts`, CLI `review-blind-pair-command.test.ts`: 기존 Soul 비교 회귀 방지. 신규 작법 packet 검증·UI 비노출·응답 이후 공개 시험 추가.
- `story-rail-reflow.test.ts`, `arc-rail-store.test.ts`: stale 근거 거부, 확정 사실·anchor 보존, 미래 구간에 한정한 수정.

각 변경의 관련 테스트와 해당 패키지 typecheck를 실행하고 필요 범위의 통합 검증을 한다. 프롬프트에 좋은 문구가 들어갔다는 문자열 검사만으로 창작 품질을 검증하지 않는다.

문제가 생기면 해당 실행에서 선택형 묶음을 끄고 기존 입력으로 돌아간다. 입력·실패·원고 후보·사람 응답은 남긴다. 과거 원고를 재작성하거나 Git reset/stash로 되돌리지 않는다. 독립 Git 루트마다 변경 파일을 검사하고 별도로 검증·커밋한다. 이번 턴에서는 계획 문서와 색인·기준 기록만 저장하며 커밋·푸시는 수행하지 않는다.

## 8. 남은 조사와 보류할 일

지금 더 필요한 근거는 일반 작법론 링크가 아니라 **이 구현으로 나온 원고, 사람이 고른 이유, 수정 전후, 연속 회차에서의 회수**다. 이 자료는 구현과 평가 과정에서 만든다.

추가 외부 조사는 실패 원인이 구체적으로 생겼을 때만 좁혀 진행한다. 예를 들어 “강한 주인공의 승리 뒤 생활 장면이 계속 설명처럼 읽힌다”면 그 기능의 원문과 수정 사례를 더 찾는다. 특정 작가의 전 작품을 읽었다고 확대 해석하거나 자료 수를 늘리는 것을 구현의 선행 조건으로 삼지 않는다.
