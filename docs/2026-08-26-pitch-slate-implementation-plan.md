# InkOS N개 피치 슬레이트 구현 계획

- 작성일: 2026-08-26
- 상태: 구현 승인
- 목표: HQ가 후보 수 `N`과 검증된 레퍼런스를 발주하고, InkOS가 비교 가능한 비정본 기획 후보를 만든 뒤 선택작만 Book으로 승격한다.

## 결론

`10개`는 예시다. 실행 계약은 `candidateCount=N`으로 받고 한 번의 실행은
1~20개로 제한한다. 후보 수가 20개를 넘으면 모델 출력 절단, 후보 간 중복,
심사 피로가 커지므로 여러 슬레이트로 나눈다.

HQ는 장르·상업 약속·후보 수와 해시로 고정된 레퍼런스를 전달하고 실행
영수증만 집계한다. 후보 본문은 HQ가 쓰지 않는다. InkOS는 후보를 하나씩
생성·검증한 뒤 `.inkos/pitch-slates/<slateId>/`에 비정본 산출물로 저장한다.
후보 생성은 Book, Story Frame, Rail, Arc, 원고를 만들지 않는다.

## 계획 안정성 감리

### 1차 반례: Book N개를 먼저 만들면 되는가

기각한다. `book create`는 작품 기반과 정본 파일을 만들기 때문에 탈락할
후보까지 작품 목록과 세션을 오염시킨다. 후보 심사 전에 필요한 것은
완성 작품이 아니라 동일한 항목으로 비교 가능한 얇은 생존 기획서다.

### 2차 반례: HQ 영수증에 모델 답변만 보관하면 되는가

기각한다. HQ는 자식 콘텐츠 소유자가 아니며 영수증은 제작물 저장소가
아니다. InkOS가 자기 실행 영역에 원자적으로 산출물을 저장하고, HQ는
자식이 보고한 경로와 SHA-256을 재검증해야 한다.

### 3차 반례: 한 번의 모델 응답에서 N개를 모두 만들면 되는가

기각한다. N이 커질수록 뒤쪽 후보가 얇아지고 JSON이 절단되며 실패 시
전체 결과를 복구하기 어렵다. InkOS는 후보별 세션을 직렬 실행하고 후보
하나가 형식 검증에 실패하면 한 차례 교정한 뒤, 모두 유효할 때만 최종
슬레이트 디렉터리를 원자적으로 공개한다.

3차 재검토 뒤에도 불변축은 다음과 같다.

```text
HQ 발주와 입력 검증
  -> InkOS 후보별 상업 피치 생성
  -> N개 완결성 검증
  -> 비정본 슬레이트 저장
  -> 사람의 폐기 / 보류 / 심화
  -> 선택작만 InkOS Book 승격
```

## 후보 계약

각 후보는 다음 항목을 동일하게 가진다.

1. 제목 후보와 한 줄 상품 약속
2. 주축 참고작과 보존할 골격
3. 주인공의 출발 신분, 반복 동사, 첫 자산
4. 1~4화 사건과 첫 보상
5. 돈·지분·권력의 A Rail
6. 관계·인정·복수의 B Rail
7. 최소 6개 Arc 상승 사다리와 보조 참고작 라우팅
8. 장기 연재 위험 한 가지와 상업성 점수

상업성 점수는 상품 약속, 1~4화 지급, 반복 엔진, A/B Rail 환전, 장편
공급량만 평가한다. 독창성, 원작과의 거리, 표면 유사성은 점수 항목으로
두지 않는다.

## 저장과 승인

```text
.inkos/pitch-slates/<slateId>/
  slate.json   # 기계 판독 가능한 N개 후보와 pending 결정 상태
  review.md    # 모바일에서도 빠르게 죽이고 살릴 수 있는 비교 문서
```

두 파일 모두 `canonStatus=non-canonical`이다. 후보를 만든 사실과 후보를
채택한 사실은 다르다. 선택 이후의 Book 생성과 기획서·Rail·Arc 확장은
새로운 사람 승인 WorkOrder로 실행한다.

## 실패 조건

- `candidateCount`가 1~20 범위를 벗어남
- `slateId`가 안전한 파일명 규칙을 위반함
- 검증된 `pitch-reference-pack` 입력이 없음
- 후보 수가 N과 다르거나 필수 항목·6개 Arc·상업성 점수가 누락됨
- 최종 산출물 경로 또는 해시를 InkOS가 보고하지 못함
- InkOS의 `.inkos/` 밖에 쓰기 발생

이 경우 HQ는 성공 영수증을 내지 않으며 불완전한 슬레이트를 심사 대상으로
노출하지 않는다.
