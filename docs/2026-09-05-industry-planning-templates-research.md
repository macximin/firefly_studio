# 업계 기획서·시놉시스 양식 조사와 Firefly 적용 후보

2026-09-05 · 외부 원문 확인 · HQ 검토용 · InkOS 생산 계약에 미적용

**권고: 한경·CJ ENM 스토리 공모의 작품 기획안을 기본 뼈대로 삼고, Screen Australia의 연속극 설계 관점을 더하자. 출판사에 보여줄 때는 텐북처럼 짧게 추려 쓰면 된다.** GitHub 자료는 Markdown과 회차 상태 표현을 참고하는 정도가 적합하다. 조사한 GitHub 두 저장소를 업계 표준이나 검증된 흥행 방식으로 취급하지 않는다.

공개된 제출 서식, 제작기관 가이드, 작법 서비스 템플릿, 개인 GitHub 프로젝트를 구분했다. 모두 같은 수준의 업계 관행 증거는 아니다. 아래 원본 네 개는 실제로 내려받았고 HWP/DOCX의 본문 및 PDF 내용을 확인했다. [출처·해시 기록](/Users/a2501/Desktop/firefly_studio/docs/evidence/industry-templates-2026-09-05/sources.json).

## 3. 무엇을 가져오고 어떻게 수정할까

아래는 출처의 문구를 번역·복제한 양식이 아니라, 현재 Firefly 요구를 반영해 새로 작성한 적용안이다. [기입 가능한 Markdown 후보](/Users/a2501/Desktop/firefly_studio/docs/2026-09-05-planning-format-candidate.md)에 빈칸 형태로 남겼다. 아직 기존 계약과 스키마에 적용하지 않았다.

| 사용할 구조 | 수정 방법 | 기존 자산과 연결 |
| --- | --- | --- |
| 작품 기획서 | 제목·장르·로그라인·키워드·인물·전체 줄거리를 유지. 독자가 반복해서 얻을 재미, WHY/WHAT/HOW, 최종 성취를 추가 | entry contract + story_frame + volume_map |
| 인물 소개 | 신상 정보보다 욕망, 자기 선택, 우위 활용, 다른 인물과의 관계를 먼저 쓴다. 내적 성장·상처는 필요한 인물만 | roles |
| 기획 의도 | 작가가 말하고 싶은 주제와 주인공이 달성할 목적을 별도 질문으로 둔다. 메시지가 없어도 독자 약속은 설명 | story_frame + authorIntent |
| 연재 구성 | 시즌/방송시간 대신 장편 구간, 큰 사건의 결과, 반복될 행동과 보상 변주를 쓴다 | anchorRail + arcRouteRail |
| Arc 카드 | 이번 목표, 선택과 우위, 사건 인과, 지급·후과를 기록. 승인한 큰 목적과 연결 | ArcPacket |
| 회차·장면 메모 | 이번에 하려는 일, 독자가 아는 정보, 실제 행동과 결과를 짧게 적는다 | 기존 회차 메모 |
| 원고 | 별도 본문으로 쓴다. 기획서의 표·검수 용어를 독자에게 노출하지 않는다 | chapter 본문 |

현재 InkOS 실행 ArcPacket은 1~3화다. 외부 양식의 시즌·에피소드·scene을 이름만 바꿔 동일한 단위로 취급하지 않는다. 큰 사건 구간과 실행 패킷의 연결을 명시한다. [현재 스키마](/Users/a2501/Desktop/firefly_studio/edge_repos/inkos/packages/core/src/arc/schema.ts:53).

기존 작품의 조합·변주는 내부 참고란으로 보강한다. 각 작품에서 **어떤 재미·사건 기능·인물 배치·보상 방식을 가져왔고, 현재 인물의 목적 때문에 무엇을 바꿨는지** 적는다. 외부 양식들이 이 작업을 자동으로 해결해 주는 것은 아니다.

특히 기존 문제를 다시 만들지 않도록 다음을 구분한다.

- 권한과 돈은 유효한 수단·보상이다. 그걸 얻고 누가 어떤 행동을 하는지 읽히게 한다.
- 큰 승리·행운·깔끔한 결산은 그대로 사용할 수 있다. 모든 구간에 손실·실패·반성을 배정하지 않는다.
- 장면표의 빈칸은 보조 질문이다. 후일담까지 갈등과 반전을 억지로 채우지 않는다.
- 가까운 Arc는 구체적으로, 먼 구간은 결과와 방향 중심으로 적는다. 모든 화를 먼저 확정하지 않는다.
- 외부 제출본은 해당 제출처 양식에 맞춘다. 내부에서는 개인정보·공모전 자격·방송용 항목을 상시 창작 계약으로 만들지 않는다.

## 4. 채택 제안

**기획서 목차는 한경 양식, 연재 설계는 Screen Australia, 짧은 검토본은 텐북을 참고하는 조합**을 권한다. GitHub의 장점은 문서 구조를 코드와 함께 다루기 쉽다는 데 있다. 그것을 한국 장르 취향의 권위로 삼지는 않는다.

실제 채택 시에는 별도 거대 바이블을 추가하기보다 기존 InkOS 문서의 표시 순서와 내용 질문을 이 후보에 맞추면 된다. 원작 분석은 Reference Lab, 창작 계획과 원고는 InkOS가 계속 소유한다. 이번 작업은 HQ 조사와 서식 후보 작성까지만 수행했다.
